# ADMIN設計ハーネス

この文書は、運営サイトの画面・状態・保存先・外部連携をまたぐ変更で、操作の無駄や画面ごとの食い違い、復旧しにくい状態を作らないための設計基準とレビュー用チェックリストです。

ADMINの変更を始めるAgentは、特に次のどれかに当てはまる場合、このハーネスを使います。

- 同じ対象の状態を一覧・詳細・編集画面など複数の場所で表示する
- 保存、承認、公開、取消、再試行など状態遷移を追加・変更する
- D1、Durable Object、GitHub、Cloudflareなど複数の保存先や外部サービスをつなぐ
- エラーや再試行のあとに復旧する手順がある

このハーネスは、[`ADMIN_DEPLOYMENT_POLICY.md`](ADMIN_DEPLOYMENT_POLICY.md)などの本番運用方針を置き換えません。運用上の固定事項と異なる場合は、固定事項に従って変更を止めます。

## 1. 利用者の意図から操作を決める

- 利用者が達成したい仕事を先に書き、内部実装上の都合を利用者の手順にしません。
- 保存するたびに版を作るなど、既存操作から自然に導ける処理は自動化し、別の「更新案を作成」操作を設けません。
- ボタンやメニューは、利用者が明確に選ぶ必要のある状態遷移だけを表します。各操作について、実行前提・変更される状態・完了後に見える結果を説明できるようにします。
- 版ID、候補ID、Worker Version IDなどの内部識別子や、候補登録・配信照合などの自動処理を編集者に意識させません。運営者に必要な障害情報は、通常操作と分けて具体的に表示します。
- 同じ状態を示す複数のボタンや、画面によって意味が変わる操作を作りません。

## 2. 正本と状態遷移を先に決める

実装前に、対象の正本、識別子、状態遷移を明記します。時刻、行の置き場所、画面の表示文言を正本の代わりに使いません。

記事編集では、保存済みの版IDを使って次の状態を区別します。

| `current_version_id` | `published_version_id` | 意味                             | 編集画面を開いたとき     |
| -------------------- | ---------------------- | -------------------------------- | ------------------------ |
| 版あり               | `NULL`                 | 保存済みの未公開記事             | 最後に保存された版       |
| 同じ版ID             | 同じ版ID               | 編集中の最新版が公開版           | その版                   |
| 異なる版ID           | 公開済み版あり         | 保存済みの編集が公開版より新しい | `current_version_id`の版 |

- 保存済み版は版IDで参照し、保存のたびに新しい版を作ります。公開Runは公開対象の版IDを固定し、その後の編集で対象版がすり替わらないようにします。
- 公開状態は「canonicalにある本文」や`updated_at > published_at`のような日時比較で推定しません。記事ごとの`published_version_id`を明示し、公開履歴とCloudflareの実配信情報を照合します。
- `current_version_id`と`published_version_id`の差は「保存済みの編集が公開版より新しい」ことを表します。査読状態、権限、公開Runの状態は別の条件として確認し、版の差だけで公開を許可しません。
- 日時は監査・表示・並べ替えに使います。記事が更新案を持つか、どの版が公開中かを決める唯一の根拠にしません。
- 候補に含まれる記事・版IDの記録と、Cloudflare切替後の公開履歴は別の事実として保存します。候補登録を公開完了と呼びません。

記事版の詳しい画面動作と公開順序は、[`EDITORIAL_WORKSPACE.md`](EDITORIAL_WORKSPACE.md)と[`EDITORIAL_ADMIN_ONLY_PUBLICATION.md`](EDITORIAL_ADMIN_ONLY_PUBLICATION.md)を正本として参照します。

## 3. 同じ状態はすべての画面で同じように見せる

変更前に、対象状態を表示・操作する全箇所を洗い出します。一覧だけ、詳細だけを直して完了にしません。

- 一覧、詳細、編集画面、通知、フィルター、検索結果、モバイル表示、関連APIを確認します。
- 状態ラベル、操作可能性、件数、警告表示は、同じサーバー側状態または共通の状態判定から導きます。各画面に独立した日時ヒューリスティックや重複判定を書きません。
- 一覧から見える操作は、詳細画面で確認できる状態と矛盾しないようにします。例えば詳細に「保存済みの未公開版あり」と出る記事を、一覧で「更新案を作成できる」と誤表示しません。
- 状態を変えるAPIは、画面のボタンの表示だけに頼らず、権限・現在状態・対象版ID・期待する遷移をサーバー側で再確認します。
- 画面に表示する状態と操作が矛盾する場合、表示文言だけを修正して隠さず、状態の正本、API応答、各画面の導出方法をたどって原因を直します。

## 4. 外部処理と障害時の復旧を設計する

外部サービスを含む処理は、どの段階で何が確定したかを分け、失敗位置ごとに利用者への影響と復旧方法を決めます。

公開フローの基本順序:

1. D1で公開対象の版IDを固定する。
2. GitHub PRを作成し、対象内容を検査して取り込む。
3. Cloudflareで候補Versionを作り、まだ本番配信は切り替えない。
4. 候補に実際に含まれる記事IDと版IDをD1へ記録する。
5. その記録が成功した候補だけをCloudflareで本番へ切り替える。
6. 100%配信された候補VersionとDeploymentを確認した後、D1へ公開履歴を追記し、`published_version_id`を更新する。

| 失敗位置                                       | 公開側の扱い                               | 復旧の基準                                                                                    |
| ---------------------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 候補内容のD1記録前または記録失敗               | Cloudflareを切り替えず、現在の公開版を維持 | D1への候補記録が成功するまで配信を止める                                                      |
| 候補記録後、Cloudflare切替前                   | 現在の公開版を維持し、候補記録を残す       | 同じ候補の状態を照合して処理を再開する                                                        |
| Cloudflare切替後、公開履歴のD1記録だけ失敗     | 読者には切替後の版が見える可能性がある     | Cloudflareの有効Version/DeploymentとD1候補記録を照合し、D1記録だけを補修する                  |
| 実配信・候補・履歴が一致しない、または特定不能 | 成功扱いにせず停止する                     | SHA、Version、Deployment、時刻、D1記録を集めて調査する。推測で再配信・rollback・promoteしない |

- 外部APIへの再試行は冪等にし、応答が失われた再試行で重複版、重複公開履歴、誤った状態遷移を作らないようにします。
- 公開切替済みの事実を直すとき、公開サイトを再度切り替えることを復旧の前提にしません。確認済みの実配信が正しければ、必要なD1記録を修復します。
- ログや診断画面には復旧に必要なrun ID、版ID、候補Version ID、Deployment ID、SHA、失敗段階を残します。秘密情報や不要な本文・個人情報は残しません。

## 5. 実装前レビュー用チェックリスト

PRの実装メモまたは作業計画で、次を埋めます。

- [ ] 利用者が達成したい仕事と、不要として取り除く操作は何か
- [ ] 正本データ、識別子、現在状態を決める条件は何か
- [ ] 状態遷移の前提、成功後の状態、失敗後の状態は何か
- [ ] 状態を表示・操作する画面、API、通知、一覧・詳細・モバイル表示はどれか
- [ ] どの判定を共通化し、どの権限・状態検証をサーバー側で行うか
- [ ] 外部サービスの各書き込みが成功・失敗した場合、何が読者・運営者に見えるか
- [ ] 重複実行、通信タイムアウト、古い版ID、同時編集、途中再開をどう扱うか
- [ ] 障害後に何を照合すれば復旧でき、何を自動実行してはいけないか
- [ ] 上記を検証するテストの入力状態と期待結果は何か

## 6. 回帰テストの基準

複数画面にまたがる状態変更では、少なくとも次のシナリオから該当するものをテストします。

- 編集画面を開くと最後に保存した版が開き、保存すると新しい版IDが作られる。
- `current_version_id`と`published_version_id`が同じ場合と異なる場合に、一覧・詳細・編集で同じ意味の状態が表示される。
- 未公開記事、公開版と一致する記事、公開版より新しい保存版がある記事、未公開・公開取消の記事を区別する。
- 古い版IDや別記事の版IDでは公開Runを開始・更新できない。Runを開始した後に別の編集版が保存されても、固定した版IDが変わらない。
- 候補記録に失敗すると本番切替が起きない。D1履歴記録に失敗した後は、実配信を照合してD1だけを補修できる。
- 一覧のボタン、詳細の状態、APIが許可する操作が同じ状態表に一致する。
- 権限不足、タイムアウト、二重送信、古い画面データを試しても、誤った状態遷移を起こさない。

テストは表示文言だけでなく、保存された版ID・状態遷移・実行された外部処理・失敗時に止まった地点を確認します。対象画面の変更では、既存E2Eを確認し、一覧から編集を開く経路を含めて検証します。

## 7. 変更後レビュー

変更後は、実装者以外の観点で次を再確認します。

1. 一覧から編集を開き、表示された版・状態・操作が同じデータに基づくこと。
2. 保存・承認・公開などの操作が、状態表で定めた遷移だけを行うこと。
3. 状態判定を別画面で重複実装していないこと。日時比較を状態の根拠にしていないこと。
4. 外部処理を止めた各地点で公開の実態とD1記録を区別でき、事実に合わせて回復できること。
5. 正常系・途中失敗・再試行・同時編集の回帰テストがあり、CIと変更範囲に合ったChrome確認が成功していること。

レビューで不一致が見つかった場合は、対象画面だけを合わせず、状態の正本と導出経路を直してから再確認します。
