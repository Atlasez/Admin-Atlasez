# 実運用受入基準

更新日: 2026-11-27

## 現状

- mainには記事アーカイブの承認フローが含まれる。メンバー受入と別系統の削除申請フローを混ぜない。
- mainを土台にしたメンバー受入候補をローカルで統合し、単体テスト88 files / 800 tests、型・静的チェック、lint、format、ADMIN build、build-info、staging config template、Wrangler dry-runが通過した。
- ローカルPlaywrightのブラウザー取得は配布元のHTTP 403で完了できていない。PRのGitHub CIでE2Eを確認する必要がある。
- 実アカウントでのstaging OAuth、全roleの操作、通知到達、バックアップ復旧は未受入。本番migrationと本番投入も未実施。

## リリースゲート

| 順序 | ゲート         | 完了条件                                                                                                                                                      |
| ---- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | ブランチとCI   | mainをbaseにしたPRで必須CIが最新commitに成功。レビューでmigration順・認可境界・メール/Discord副作用を確認。                                                   |
| 2    | staging構成    | staging専用Worker/D1/OAuthをread-onlyで照合。設定のproduction比較値はrepositoryに置かず、環境変数またはsecret storeから与える。実行commitと配信commitが一致。 |
| 3    | 実ユーザー受入 | 専用アカウントで応募、承認/却下、招待、初回ログイン、role別画面とAPI、停止/復帰、監査履歴を確認。通知先は承認済みsandboxだけ。                                |
| 4    | 運営準備       | 主担当/代理、対応期限、問い合わせ先、個人情報保持期間、権限表、障害時の停止/復旧、backupのRPO/RTOを決め、記録する。                                           |
| 5    | データ移行     | 現行D1 migration履歴を再読込し、backupと隔離復元を検証。migration適用はD1所有者の明示承認後に別作業として行う。                                               |
| 6    | 本番GO         | 上記証跡を責任者が確認し、対象commit、戻し方、監視時間、担当者を記録してから本番deployする。                                                                  |

## 停止条件

- 必須CI失敗、対象commit不一致、権限漏れ、stagingから本番データへの接続、未承認のメール/Discord送信、backup復元失敗のいずれかで停止する。
- migrationや本番設定変更はコードdeployと分ける。GO記録とD1所有者承認がない状態では適用しない。
- 受入試験で使う個人情報はsynthetic dataに限定し、実応募データを検証用環境へ複製しない。
