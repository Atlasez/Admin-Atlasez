# 定期処理の監視と切り分け

## 目的と対象

運営者が `/admin/developer/` で、定期処理の最終成功・失敗、連続失敗、完了を確認できない処理、未完了キューを確認できるようにする。対象APIは `GET /api/admin/developer/diagnostics`。既存の開発者閲覧権限を使用し、一般会員に集計や実行記録を公開しない。

この変更は監視記録の追加とコードの分割である。既存のcron、業務キュー、再試行・公開・保持期限の条件は維持する。保持期限方針の承認や変更、監視画面からの再送・公開切替、外部へのアラート送信は含まない。

## 設計と正本

| 対象                           | 正本・責務                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------- |
| ジョブの対象・実行間隔         | `src/lib/admin-scheduled-job-health.ts` の固定16種類と既存のWorker cron設定     |
| cronごとの実行・例外処理       | `src/lib/admin-scheduled-jobs.ts`。Workerは業務関数を渡す                       |
| 実行の観測結果                 | D1 `admin_scheduled_job_health`。各ジョブ1行、最大16行                          |
| キューの未完了・再試行・要対応 | 既存業務テーブル。`src/lib/admin-scheduled-job-queues.ts` が集計だけを行う      |
| 状態判定                       | API側の共通モジュール。UIで独自の期限判定を重ねない                             |
| 表示・再取得                   | `src/scripts/admin-developer-diagnostics.ts`。Astroページは構造とスタイルを持つ |

開始時にrun IDを割り当て、最新runの状態・終了時刻・所要時間・失敗回数の更新には `current_run_id` の一致を要求する。遅れて完了した古いrunが新しい実行状態を上書きしない。開始書き込みの遅延でも、古い開始時刻による上書きを拒否する。一方、最後の成功・失敗時刻は並行していたrunも含めて最大時刻を記録する。新しいrunが0件で終了した後に古いrunが失敗しても、その失敗を隠さない。全実行の監査履歴や業務ロックには使用しない。

開始・終了に各1回のD1書き込みを追加する。監視の書き込みやログ出力が失敗しても業務関数の戻り値・例外を維持する。業務関数内部で捕捉する失敗は、固定の結果コードで監視に報告する。メール等の返却値 `failed` / `skipped` も観測に反映し、単なるPromiseのresolveを成功の根拠にしない。

### 表示する状態

| 観測                       | 表示   | 成功時刻・失敗回数                                 |
| -------------------------- | ------ | -------------------------------------------------- |
| 開始後、完了待ち           | 実行中 | 前回の成功・失敗を保持                             |
| 正常完了                   | 正常   | 成功時刻を更新し、連続失敗を0に戻す                |
| 一部失敗・状態未確認の報告 | 要確認 | 失敗時刻・連続失敗を更新                           |
| 業務関数が例外を投げた     | エラー | 失敗時刻・連続失敗を更新。既存の例外処理に従う     |
| 設定不足等でスキップ       | 要確認 | 成功として記録せず、以前の成功時刻・失敗回数を保持 |
| まだ観測記録がない         | 未確認 | 成功を推定しない                                   |
| 監視テーブルを読めない     | 未確認 | `available=false`。他の診断は継続                  |

同じrunで後から成功が報告されても、先行する一部失敗やスキップを消さない。最後の失敗が最後の成功より新しければ、最新runの状態がsuccessでも要確認とする。連続失敗回数は最新runとして採用された終了記録に対する値であり、重複実行全件の失敗総数ではない。

正常終了後に新しい結果が届かない場合と、開始したまま完了しない場合は、予定間隔の3回分を超えると「要確認」にする。

| 予定間隔 | 要確認になる経過時間 |
| -------- | -------------------- |
| 1分      | 3分超                |
| 2分      | 6分超                |
| 5分      | 15分超               |
| 1時間    | 3時間超              |

5分cronの既存 `Promise.allSettled` と、その他のcronの `Promise.all` による例外伝播を維持する。個人情報の保持期限処理は従来どおり1時間のバッチで実行し、`ADMIN_PERSONAL_DATA_RETENTION_ENABLED` の意味も変更しない。

## キューの読み方

「未完了」は再試行待ち・処理中を含む。「再試行待ち」はその内数。「要対応（24時間）」は直近24時間に更新された失敗・要対応状態の件数であり、未完了への加算値ではない。最古時刻・待機時間は各キューの次の基準に従う。将来の再試行予定だけを理由に滞留とは判定しない。

| キュー          | 集計対象・最古時刻                                                                     |
| --------------- | -------------------------------------------------------------------------------------- |
| 記事公開        | 記事ごとの最新の公開・公開取消run。開始時刻を基準とし、下書きと置き換わった履歴を除外  |
| 応募メール      | pending / retry / sending。キュー登録時刻                                              |
| ゼミ応募メール  | pending / retry / sending。キュー登録時刻                                              |
| Discord通知     | pending / retry / sending。キュー登録時刻                                              |
| タスク通知      | 現在のタスク・通知時刻・宛先・有効な所属に対応する送信記録。キュー登録時刻             |
| Discord参加設定 | 受理済み応募の参加設定失敗・処理中。次回再試行予定時刻、処理中・予定なしは最終更新時刻 |
| 会員手続き      | 適用日を迎えたscheduledの手続き。適用予定時刻                                          |
| 定期タスク作成  | 有効で次回予定時刻を迎えたテンプレート。次回作成予定時刻                               |
| 予約公開        | 予定時刻を迎え、公開済みでなく、公開PRが未設定の記事。公開予定時刻                     |

通常は実行予定から15分超、記事公開は開始から60分超で滞留とする。最新公開runの失敗・担当者確認待ち、次回再試行予定のないDiscord設定失敗、会員手続きの実行エラー、タスク通知の再試行期限切れ、エラーで作成停止になった定期タスクは時間経過を待たず要確認とする。これらは24時間を超えても状態が解消されるまで警告を残す。定期タスク停止時には更新時刻が変わらない既存仕様があるため、24時間内の件数だけで正常とは判定しない。キューごとに取得エラーを分離し、読めなかった件数は0ではなく未確認として返す。

集計は件数・時刻だけを返す。本文、メールアドレス、Discord ID、例外メッセージは監視APIの集計や新しい監視ログに含めない。確認先は「公開担当」「メール担当」等の役割であり、実在の担当者名を推定しない。

画面は既存APIの応答に監視項目がない場合も未確認を示す。再取得の開始時に古い結果を消し、403・通信失敗時に以前の正常表示や権限付きリンクを残さない。文字列は `textContent` で描画し、API応答をHTMLとして実行しない。

## 障害時の確認と復旧

| 状況                 | 確認・復旧                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------- |
| 監視データ未取得     | migration適用記録とD1接続を確認。未適用なら下記の導入手順に従う。次回cronの記録を確認する |
| 実行結果の更新停止   | Workersの定期実行ログ、最後の開始・終了時刻、cron設定を照合する                           |
| 実行エラー・一部失敗 | 該当ジョブと時刻、固定エラーコード、既存業務画面の状態を確認する                          |
| キューの要確認       | 現在の担当者確認待ち、再試行予定・期限、連携設定を既存画面で確認する                      |
| 設定不足             | 必須設定を正規の手順で確認する。値を診断画面やログに貼り付けない                          |
| 成功へ復帰           | 次のcronで成功時刻と失敗回数0を確認し、キューの要対応も解消したか別に確認する             |

`admin_scheduled_job_started` / `admin_scheduled_job_finished` ログにはjob ID・run ID・時刻・結果・記録可否を出す。`observation` は `recorded` / `not_recorded` / `unavailable`。遅れた古い開始記録や更新対象のない記録は `not_recorded`、DB障害は `unavailable` として区別する。ログの業務結果と監視記録の成否は別の項目として確認する。

ジョブが正常でも、外部サービスでのメール到達・Discord反映や公開Workerの100%配信まで保証するものではない。公開の不一致時は既存のSHA・Version・Deployment照合手順に従い、推測で再公開・rollback・promoteしない。監視画面自体は再送や状態修正を行わない。

## migrationと導入順

追加するmigrationは `0142_admin_scheduled_job_health.sql`。既存の業務テーブルを変更・削除せず、固定ジョブID・結果コードを制約した監視テーブルだけを追加する。0140・0141は別作業の番号を予約しているため再利用しない。0142はそれらの業務変更に依存しない。

1. PRでmigration、既存Workerとの互換性、共有D1への影響をレビューする。
2. `atlasez-reports` のバックアップと未適用migration一覧を取得・記録する。バックアップに含まれる業務データは公開しない。
3. 適用対象一覧を確認し、承認されたmigrationだけを適用する。通常のbuild/deployにmigrationを組み込まない。
4. `admin_scheduled_job_health` の作成を確認し、適用時刻と対象DBを記録する。
5. CI・レビュー成功後にmainへ取り込み、既存のCloudflare Workers Buildsで `atlasez-admin` を配信する。
6. build-infoのSHA、配信Version・100%配信、認証済み `/admin/developer/` を確認する。導入直後の未実行は未確認で正常。全16種類の最初の記録には1時間cronの到来まで必要な場合がある。

DB変更前の確認例（読み取りのみ）:

```bash
npx wrangler d1 migrations list atlasez-reports --remote --config wrangler.admin.jsonc
```

他の未適用migrationがある状態で一括適用を推測実行しない。本番変更・配信は [`ADMIN_DEPLOYMENT_POLICY.md`](ADMIN_DEPLOYMENT_POLICY.md) と [`ADMIN_CHANGE_WORKFLOW.md`](ADMIN_CHANGE_WORKFLOW.md) に従う。

問題時は配信を止め、レビュー済みmainで監視変更をrevertする。旧Workerは追加テーブルを参照しないため、テーブルを残しても業務上の互換性がある。復旧のために業務データを変更したり、監視テーブルを急いで削除したりしない。

## 検証対象

- 実SQLiteでmigrationの再適用・既存データ維持、成功→失敗→回復、設定不足、監視DB不在、重複runの開始・終了競合、期限超過、秘密値の非記録。
- cronごとの対象・例外伝播維持と、Worker入口から内部で捕捉された失敗が観測されること。
- 9種類のキューの空・欠落、状態別件数、未来再試行、最古時刻、対象外タスク・宛先・所属、読み取り専用性。
- 診断APIの権限境界、正常・未確認、監視テーブル欠落時の他の診断継続。
- UIの状態別表示、再取得失敗・復旧、403、旧API、HTML安全性、390px表示。ブラウザが起動しない環境ではE2E成功と扱わず、CIまたは実ブラウザでの確認をマージ前に完了する。

対象を分割した段階的な保守性改善とし、巨大なWorkerに残る全業務関数の一括移動は行わない。今後の機能変更時に、業務境界ごとに既存テストを維持して分離できる構成にする。
