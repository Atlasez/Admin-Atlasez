# 定期処理のDiscord異常・復旧通知

## 有効化と対象

#635の監視スナップショットに基づき、5分cronの業務処理の終了後に通知キューを更新する。専用の非公開運営チャンネル向けCloudflare Secret `DISCORD_ADMIN_HEALTH_WEBHOOK_URL` を正規手順で設定するまで無効。既存の分野別・進捗用Webhookには送信しない。設定値はDB、ログ、ブラウザ、GitHubに記録しない。Cloudflare設定はこのPRでは変更しない。

15ジョブ・8キューを対象とし、通知自体のDiscordジョブとキューは自己増幅防止のため除外する。除外した2項目も従来どおり開発者画面で確認する。状態の正本は#635の診断と既存のDiscord通知キューで、警告・エラーだけを異常、正常だけを復旧とする。未確認・実行中は新規異常にも復旧にも数えない。

## 状態と再試行

- 異常・未登録: incidentを開き異常通知を1件登録。
- 異常・登録済み: 同一incidentの通知は追加しない。
- 正常・異常通知が送信済み: 復旧通知を1件登録してincidentを閉じる。
- 正常・異常通知が未送信: 送信結果の確定までincidentを維持する。
- 正常・異常通知が最終失敗: 誤解を避けるため復旧通知を出さずincidentを閉じる。
- 未確認・実行中: incidentの開閉なし。
- 古いスナップショット: 新しい観測を上書きしない。

D1 batchの5文をトランザクションとして実行し、観測時刻のwatermark、incidentの登録、通知の登録、復旧を同時に確定する。状態は最大23 incidentとwatermark 1行。通知IDはincidentとsignalに基づく固定dedupe keyを使用する。外部送信は既存のDiscord通知ジョブだけに任せる。HTTP成功応答の消失などでは既存再試行による外部側重複があり得るため、exactly-once送信は主張しない。通知は観測時刻付きで、既に状況が変化している場合は開発者画面を確認する。

個人名、応募情報、記事本文、例外、秘密値は通知に含めず、固定の処理名・確認先の役割・観測時刻・診断画面URLのみを送信する。メンションは既存送信機構で無効。送信失敗時は既存キューの再試行・停止条件に従う。自己通知不能は開発者画面およびWorkerログで確認する。

## 導入・停止

`0143_admin_scheduled_health_alerts.sql` は追加型migration。0133（Discord通知）・0142（監視）を前提にし、0140/0141の業務変更は取り込まない。番号重複・未適用migration・D1バックアップ・旧Worker互換性を確認し、承認済みmigrationだけ適用する。#635の本番適用・レビュー・CI、続く本PRのCI・レビュー・migration適用が確認されるまでmainへマージしない。通常配信は既存Workers Buildsのみ。

本番Worker配信後に認証済み診断画面のSHA・状態を確認する。専用Webhookの有効化は宛先と通知運用を運営者が確認した後、別途実施する。Webhookを未設定に戻すと新規incidentの登録と警報の新規送信が止まる。無効なWebhookも同様に扱う。既存の警報キューは保留され、停止中に再試行回数を消費しない。通常のDiscord通知の配信は継続する。有効化後に保留中の通知を再開するため、宛先変更時は旧incident・キューを確認し、進行中の外部送信が即時取り消されるとはみなさない。Webhookを設定していない環境では通知の本番到達を成功扱いしない。

回帰時は新規通知を停止し、レビュー済みmainでコードをrevertする。追加テーブルは残し、既存業務データの削除・再送・公開切替を推測で行わない。
